The TypeScript and Vue code of DrinkIt follows one rule set, which ESLint runs with `--max-warnings 0`: a finding
fails the commit and the CI, and no warning waits to be fixed later. The set comes from the
[Google TypeScript Style Guide](https://google.github.io/styleguide/tsguide.html), the
[Vue style guide](https://vuejs.org/style-guide/) and the strictest presets of typescript-eslint, with rules of our
own for server-side rendering, on top of Nuxt's own ESLint config. `@drinkit/eslint-config`, under
`code-analysis/eslint`, exports it as `drinkitEslint()`, which each package calls from its
`eslint.config.ts`, as the [frontend architecture](../../2.architecture/7.frontend-architecture.md) describes. Read
this page before you change a rule, or when a finding surprises you.

The code renders on the server first, so the rule that matters most is the one a test would miss: code that runs
fine in the browser can leak one user's state to another on the server.

## 📏 Formatting

ESLint Stylistic formats the TypeScript and the templates, Stylelint Stylistic the CSS, which ESLint does not read,
with no Prettier: each tool fixes and checks, and the pre-commit hook applies their fixes before the commit.

| Rule | Reason |
|---|---|
| A semicolon ends every statement | Automatic semicolon insertion breaks a line that starts with `(` or `[` |
| Single quotes, a trailing comma on multiline, parentheses around arrow parameters | A diff of one line stays one line |
| Indent of 2, inside `<script>` and `<style>` as inside `<template>`, lines of 120 at most, `1tbs` braces | The Vue and Nuxt docs indent by 2, a `.vue` block reads the same whatever its tag, and 120 matches the Kotlin code |
| One blank line between logical blocks, never two | As in the Kotlin code |

## 🔤 TypeScript

| Rule | Reason |
|---|---|
| Explicit imports, `vue/no-undef-components` | Each name says where it comes from: a component used without an import fails the lint, a composable the type check |
| Imports ordered: `vue`, `#imports` and `#components`, `@drinkit/*`, `~/*`, relative, each group alphabetical | A file's dependencies read in the same order everywhere |
| `consistent-type-imports` | A type import leaves no trace in the bundle |
| Named exports only, except the files Nuxt reads by their default export | A rename follows the name across files |
| A named function is a declaration, a callback an arrow | A declaration reads as a function at a glance, and is hoisted |
| `interface` for an object, `type` for a union, `T[]` for a simple array type | One way to write each shape |
| No `any`, no `!`, no `as` on an object literal | Each bypasses the type check, where `unknown` and a type guard keep it |
| No `@ts-ignore` nor `@ts-nocheck`; `@ts-expect-error` with a reason, in tests only | A silenced error stays silent after its cause changes |
| No `enum`, a union of string literals, which the compiler enforces through `erasableSyntaxOnly` | An `enum` emits code and cannot be stripped as plain types are |
| `eqeqeq` | `==` converts types before it compares |
| camelCase, PascalCase for types, UPPER_CASE for constants, no `I` prefix, `_` for an unused parameter | The Google guide's names |
| `no-floating-promises`, `no-misused-promises`, `switch-exhaustiveness-check` | A promise nobody awaits loses its error, a `switch` that misses a case of a union compiles |
| `no-console` | Console output reaches nobody in production, and shows its data to anyone who opens the console |
| No `Intl.*Format` nor `toLocale*String` | Numbers and dates follow the locale through the i18n formats |
| An `eslint-disable` comment gives its reason, and an unused one fails | A disabled rule stays explained, and goes once the code no longer needs it |
| `eslint-plugin-compat` on `.browserslistrc` | An API the supported browsers lack fails the lint, not the user |
| A `.vue` file in PascalCase, a page or a layout and a `.ts` file in kebab-case, a composable `useX.ts` | The Vue style guide and the Nuxt routes |

## 🧩 Vue

| Rule | Reason |
|---|---|
| The `recommended` rules of the Vue style guide, multi-word names except pages and layouts | A component name never collides with an HTML element |
| Props and emits declared by type, `useTemplateRef`, no empty block | One way to declare each, checked by the compiler |
| `<template>`, then `<script>`, then `<style>` | The markup is what a reader opens a component for |
| No `v-html` | Interpolation escapes, `v-html` does not |
| Every emitted event declared, every prop used | A component's contract is what it declares |

## 🖥️ Server-side rendering

These rules are our own, written in `code-analysis/eslint` with their tests.

| Rule | Reason |
|---|---|
| No reactive state at module level | The server shares a module between every request: one user would see another's state. `useState` is per request |
| No browser global outside `onMounted`, `import.meta.client` or an event handler | `window`, `document` and `localStorage` do not exist on the server |
| No `async` composable | After its first `await`, a composable has lost its component and its Nuxt app |
| A `use*` function calls Vue, Nuxt or another composable | A function without reactivity is a plain function, and is named like one |

## 🧪 Tests

| Rule | Reason |
|---|---|
| No `vi.mock`, `mockNuxtImport` nor `mockComponent` | A module mock replaces the code under test, so the test checks its wiring: it replaces a boundary instead, such as the HTTP call |
| The `recommended` rules of Vitest and Playwright, no fixed wait in Playwright | A test that sleeps is slow and still flaky |
| A test file sits under `test/unit`, `test/nuxt` or `test/ui` | Elsewhere, no Vitest project nor Playwright finds it, and it never runs |

The [frontend tests](../2.testing/5.frontend-tests.md) say how the frontend is tested.

## 🔧 Where the rules run

The pre-commit hook fixes the staged files and refuses the commit on what it cannot fix, a Claude Code hook lints each
file an agent edits, and CI lints every package with its `lint` script, which fixes nothing. `pnpm lint:fix` fixes a
whole package. The [hooks](../../6.coding-assistants/2.hooks.md) page describes
both hooks. A rule changes in `drinkitEslint()` or `@drinkit/stylelint-config`, with its line on this page.

A starter that brings a concern brings its rules, such as a ban on bare strings in templates for translations.
