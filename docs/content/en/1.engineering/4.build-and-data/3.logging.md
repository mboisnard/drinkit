The code logs through [kotlin-logging](https://github.com/oshai/kotlin-logging) on Logback, the logger of Spring
Boot, with `private val logger = KotlinLogging.logger { }` in each class. The `observability-starter` sets the
format: plain text on a developer's machine, one JSON object per line everywhere else. Read this page before you add
a log or deploy an environment. [ADR 016](../../2.decisions/016-observe-through-micrometer-and-export-over-opentelemetry-on-demand.md)
records why Micrometer and OpenTelemetry.

## 🧾 Plain text locally, JSON elsewhere

A log platform such as Datadog reads a line of plain text as one event: a stack trace of forty lines becomes forty
events. A JSON line keeps the whole event, its level and its fields together. A person reads plain text faster, so
the developer's machine keeps it.

An environment turns JSON on with one variable, read by the
[structured logging](https://docs.spring.io/spring-boot/reference/features/logging.html#features.logging.structured)
of Spring Boot:

```bash
LOGGING_STRUCTURED_FORMAT_CONSOLE=logstash
```

We use the Logstash format: Datadog maps its `level`, `message` and `logger_name` fields without a remapper, which the
`log.level` of the ECS format needs. Each line also carries `application`, the `spring.application.name`.

Once the export of the `observability-starter` is on and its logs endpoint set, each line also leaves over
OpenTelemetry, with its trace and span, to the platform that ADR 016 names. The console keeps it all the same.

## 🔗 Fields of every line

Each key of the MDC (the map of values that Logback attaches to every log of a thread) becomes a field of the JSON
line. These keys are set for each request:

- `traceId` and `spanId`, by Micrometer Tracing, which the plain text also shows after the level. Every line logged
  during one request shares its `traceId`, even when the export to OpenTelemetry is off.
- `user.id`, by the `security-starter`, once the caller is signed in.
- `visitor.id`, by the `security-starter`: the browser behind the request, signed in or not, kept by a cookie for
  30 days after its last visit.

Every error answers a problem detail with the same `traceId`: the `observability-starter` adds it to whatever Spring MVC
answers, and the other starters hand their refusals to Spring MVC. An unexpected failure answers a 500 problem that
keeps its message out, logged with its stack trace. A user who reports an error gives the `traceId`, and the logs of
that request come up in one search. The MDC lives on its thread: work handed to another thread, such as a platform
event, starts without these keys.

## 🌐 The Nuxt app

The Nuxt app logs what goes wrong in the browser: the `observability-starter` catches each error the app leaves
unhandled and logs it once through [consola](https://github.com/unjs/consola), the logger of Nuxt, with the
`status`, the `title` and the `traceId` of its problem detail. That `traceId` is the backend's, so the line leads to
the logs of the request, and the toast the user sees quotes it as a reference. The line stays in the browser's
console until an alerting tool listens to the `drinkit:error` hook, as the
[README of the starter](https://github.com/mboisnard/drinkit/blob/master/tech-starters/frontend/observability-starter/README.md)
shows.

An error of a server render is logged by Nitro, the server of Nuxt, in plain text with the problem detail and its
`traceId`. An app rendered in the browser alone has no such server, and the starter covers it all the same.

## 🙈 What never reaches a log

No email, sign-in code, token, cookie or session id: the
[security principles](../../3.reference/2.security/1.principles.md#security-events-in-the-logs) list the rule. A user appears by their
id only. A SQL query is logged with a `?` for each bind value, never the value.
